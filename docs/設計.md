# 設計

## 構成

```text
app.py                画面の入口
config/checkpoints.toml  分野別の確認観点（編集で質問・章立てが変わる）
definereq/
  schema.py           状態・種類の定義
  project.py          ID採番、要件の版管理、分割・統合
  config.py           上限値、環境変数
  ingest/             資料読込（形式別、安全確認、版付きの登録）
  media/              録画の検証、音声の取り出し、文字起こし
  logic/              業務ロジック
    continuity.py     会議、引き継ぎ、新しい情報の振り分け
    evidence.py       根拠の照合
    agreement.py      合意、追加要望、履歴
    checks.py         観点の切替、曖昧語、非機能、矛盾、影響、残件
    baseline.py       基準版、再確認
    why.py            「なぜこの仕様か」
    guidance.py       状況案内の判定（AIを呼ばない）
    intake.py         AI候補の反映先、分類候補、分割案、案件情報への反映
    diffview.py       変更前後の差分
  ai/                 AIの呼び出しと検証（guidance.py は状況案内の補足）
  usage/              利用記録、有料処理の関門
  export/             共有資料の組み立て、Word、Excel、JSON
  demos/              3件のデモとサンプル資料
  ui/                 画面
```

UI、読込、音声、検索（why）、AI、分野別観点、業務ロジック、保存、出力を分けています。業務ロジックは Streamlit に依存しないので、画面なしでテストできます。

## 状況案内の設計

判定はプログラムで行い、画面表示や移動ではAIを呼びません。AIの補足は人がボタンを押したときだけ実行します。

| 区分 | 内容 |
|---|---|
| プログラムの判定 | 未入力、資料と録画の状態、未確認の候補、判断待ち、追加要望の状態、根拠と期限の未設定、再開、表示中の画面 |
| AIの補足 | 重要な不足情報、対立の説明、確認する質問、見直す論点 |
| 主な案内の選び方 | 今の画面に関連する案内を先にし、次に固定の順位で並べる。主な案内は1件、補足は開閉式。進捗率は使わない |
| 重複の防止 | 状態の指紋（案件内容のハッシュ値）が同じ結果があれば、AIを呼ばずに再利用する |
| 古い案内 | 状態の指紋が変わった補足は「以前のAI補足」として分けて表示する |
| 失敗時 | プログラムの案内はそのまま表示し、通常の操作を続けられる |

案内は案件データを変更しません。要件の確定、合意、判断者、期限、仕様変更は行いません。利用者が指定した段階をAIが上書きすることもありません。

## 実案件の流れの設計

| 区分 | 内容 |
|---|---|
| メニュー | 上位は作業単位の5つ（案件ホーム、会議の準備、記録を取り込む、要件を整理・判断、共有・変更管理）。選んだ作業の機能だけを表示する。機能は削除していない |
| 案件の段階 | 未登録、情報あり未解析、確認した範囲で検出なし、確認事項あり を区別する（`guidance.phase`） |
| AIへの入力 | 案件情報と会議準備の情報を確かさ付きで渡す。実行前に参照内容を画面に表示する。内部メモと選んでいない資料は渡さない |
| 候補の反映先 | 候補の種類ごとの反映先を `intake.ROUTES` で定義する。反映は人の操作のみ |
| 判断と要件の合意 | 別の状態のまま、合意記録の直後に反映の確認欄を出す。判断は対象の版を `target_versions` に記録し、版が異なる要件には反映しない |
| 次にすること | 判定は案件の状態で共通にし、開いている画面では変えない。議事録の有無、解析済みか、未処理候補、利用者が選んだ作業の段階を使う |
| 未決事項 | `share.open_items` が質問・確認事項、要件の未確認事項、判断待ち、論点、追加要望、矛盾候補、依頼を集約する。文書・Excel・出力前確認は同じ結果を使う |
| 文書の参照先 | 背景・目的は案件情報を参照する。会議準備やAI候補の内容は、人の確認後に反映する。内容が異なるときは上書きせず差分を示す |

## 主な設計判断

| 判断 | 理由 | 検討した別案 |
|---|---|---|
| 案件はdictのままJSONで保持 | 初学者でも読みやすく、保存形式と一致する | クラス化：コード量が増える |
| デモは固定JSONではなく、実ファイルを読み本番のロジックで構築 | デモが動く＝ロジックが動くことになる。根拠の照合も実際に行われる | 固定JSON：ロジックの変更で乖離する |
| 「なぜこの仕様か」はプログラムで組み立てる | 無料で動き、創作が起きない。理由がなければ記録なしと答えられる | LLM回答：根拠にない説明の危険と費用 |
| AIの出力は全て「候補」 | 合意の自動確定を構造的に防ぐ | 直接登録 |
| 引用をプログラムで照合 | AIの引用の創作を検出する | AIを信用する |
| 入力にない数値に印を付ける | 数値の創作を検出する。自動で削除はせず人が判断する | 検出しない |
| 矛盾検出は文型の照合。同じ指標・同じ条件の値の違いのみ「明確な矛盾」 | 両立可能な条件まで断定しない | 全てAI判定 |
| 利用記録はDBのトランザクションで予約 | 確認と書込を一度に行い、並行実行でも超過しない | ファイル追記：同時実行に弱い |
| 公開環境の利用記録は非公開データセット | Spaces の外部通信が80/443/8080のみで、5432番が使えない可能性があるため | 外部PostgreSQL：代替として残す |
| デモの閲覧専用は部品の呼び出しを1か所で包む | 画面ごとの条件分岐を書かず、許可の漏れを防ぐ | 各画面で分岐 |
| 未確認の情報だけでは合意できない | 話者未確認の発言で要件が確定するのを防ぐ | 警告のみ |
| 矛盾は検出時の版と文章を保存 | 後で要件が変わっても当時の指摘を説明できる | 現在の文章のみ表示 |
| トップへ戻っても案件を保持する | 不正なファイルの読込や誤操作で作業を失わないようにする | トップへ戻ると破棄 |
| 候補の振り分けは要件を書き換えない | 補足と変更候補は追加要望として受け付け、判断を経て反映する | 候補から直接更新 |
| 案内の注目カードは案件データから取得する | 創作と、後の結論の先取りを防ぐ。データがなければテストが失敗する | 説明文を固定で書く |
| 有料処理は全て1つの関門を通す | 設定不備が無料機能へ波及しない | 各所で判定 |
| 録画はPyAV | 外部コマンドを実行せず、ファイル名経由の命令実行が起きない | ffmpegコマンド |
| 音声は16kHzのWAVで10分ごとに分割 | 外部APIの25MB上限に収まり、エンコーダーに依存しない | MP3圧縮 |
| AIの呼び出しに安全判定時の自動切替（`fallbacks`）を設定 | 要件文書が誤って断られた場合に止まらない | 指定なし |

## データの流れ

```text
資料・録画 → 位置付きの単位 → （選択した単位のみ）AI → 候補 → 人の採否 → 要件
要件 → 意見調整 → 判断（人が合意を記録） → 基準版 → 共有資料
追加要望 → 影響調査 → 判断 → 反映（確認待ちへ戻る） → 履歴 → 再確認
登録情報 → 「なぜこの仕様か」の回答
```

## 安全の工夫

| 脅威 | 対策 |
|---|---|
| 資料中の命令 | 本文を `<資料>` タグのデータとして渡し、従わないよう指示。AIに道具を渡さない |
| 秘密情報 | 環境変数のみ。`.gitignore` と反映スクリプトで除外 |
| マクロ | 本文のみ読み、実行しない。`.xlsm` 等は拒否 |
| 圧縮爆弾 | 要素数、展開量、圧縮率を確認 |
| ファイル名 | パスと制御文字を除去。一時ファイルはランダム名 |
| HTML注入 | 利用者の文字は `html.escape` |
| Excel数式注入 | 危険な先頭文字に `'` を付け、文字列として保存 |
| 利用者間の混入 | 案件はセッションごとに分離。サーバーへ保存しない |
| 内部メモ | 既定で文書・Excelへ出力しない。AIへ送らない |
